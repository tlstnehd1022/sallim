# sallim (살림)

> 한 가구(household)의 가구원들이 함께 쓰는 살림 관리 앱.
> 집안일 · 캘린더 · 가계부를 하나로 묶는다.

개인 포트폴리오 프로젝트입니다. 백엔드 개발자로 일한 지 9년 차이고, Java/Spring/Oracle 기반 금융 시스템 경험을 Kotlin/Spring Boot/DDD로 확장하면서, 실제로 배우자와 함께 쓸 수 있는 앱을 만드는 것을 목표로 진행하고 있습니다.

---

## 왜 이 프로젝트인가

원래는 "집안일 관리 앱", "가계부 앱", "일정 관리 앱" 세 개의 별도 아이디어였습니다. 설계 과정에서 세 도메인이 결국 같은 기반(가구, 가구원, 공유, 실시간 동기화)을 필요로 한다는 걸 확인하고 하나로 통합했습니다.

- 집안일 관리 하나만으로는 DDD·CQRS·EDA 같은 아키텍처 패턴을 쓸 명분이 약합니다. 도메인이 셋(집안일/캘린더/가계부)이 되면서 바운디드 컨텍스트 분리가 실제로 필요한 문제가 됩니다.
- 가계부 도메인(거래·정산·분담·잔액)은 핀테크 기업 면접에서 훨씬 설득력 있는 이야깃거리가 됩니다.

**타깃**: 카카오뱅크, 토스/토스뱅크/토스페이먼츠 등 국내 핀테크 서버 개발자 포지션. 기술 스택과 아키텍처 판단 대부분이 두 회사의 채용 공고 요구사항을 기준으로 결정되었습니다.

---

## 핵심 차별점 — 청결도 모델

집안일 앱은 대부분 "체크리스트" 아니면 "타이머 기반 알림" 둘 중 하나입니다. sallim은 둘을 결합한 계산 모델을 씁니다.

```
시간 경과 → 주기 도래 → 할 일 인스턴스 자동 생성 → 미완료 누적 → 방이 더러워짐

먼지 점수 = f( Σ 미완료 할 일마다 (1 + 지연일수 × 계수) )
```

- 순수 시간 기반 모델(할 일이 안 밀렸는데도 방이 더러워 보임)과 순수 완료개수 기반 모델(8일 밀린 것과 14일 밀린 것을 구분 못 함)을 각각 검토한 뒤, 두 모델의 단점을 상쇄하는 통합안으로 확정했습니다.
- 방마다 다른 반복 주기(`RecurrencePolicy`)를 가지며, 미완료가 오래될수록 UI에서 점진적으로 더러워지는 시각 효과로 이어집니다.

## 아키텍처

### 바운디드 컨텍스트 (모듈러 모놀리스)

```
┌─────────────────────────────────────────┐
│  household (공유 기반)                     │
│  가구 · 가구원 · 권한 · 동기화               │
└─────────────────────────────────────────┘
        ↑            ↑             ↑
   ┌────┴───┐   ┌────┴────┐   ┌───┴────┐
   │ chore  │   │calendar │   │ ledger │
   │ 집안일  │   │  일정   │   │ 가계부  │
   └────────┘   └─────────┘   └────────┘
```

- 각 컨텍스트는 `household`를 공유하되 서로 직접 참조하지 않습니다. 통신은 도메인 이벤트(Kafka)로만 이루어집니다.
- 배포는 하나의 Spring Boot 프로세스(`bootstrap` 모듈이 조립)이지만, 컴파일 단위는 도메인별로 분리되어 있어 필요 시 특정 컨텍스트를 독립 서비스로 분리할 수 있는 구조입니다.
- DB도 물리적으로는 하나(MySQL)지만 도메인별로 스키마를 분리해, 한 도메인의 스키마 변경이 다른 도메인에 영향을 주지 않도록 격리했습니다.

**왜 처음부터 MSA로 가지 않았는가**: 개인 프로젝트 규모에서 마이크로서비스로 분리하면 얻는 이득(장애 격리, 팀별 독립 배포) 없이 복잡도(분산 트랜잭션, 네트워크 통신, 다중 배포 파이프라인)만 늘어납니다. 대신 바운디드 컨텍스트 경계와 이벤트 기반 통신을 처음부터 강제해, 규모가 커지면 언제든 분리 가능한 구조를 만드는 쪽을 택했습니다.

### 컨텍스트 내부 계층 (Hexagonal Architecture)

```
        HTTP 요청
            ↓
          api            REST 컨트롤러, 스케줄러 트리거
            ↓
      application         유스케이스 조율
            ↓
        domain            순수 도메인 로직 — 프레임워크 의존 없음
            ↑
      infrastructure      JPA, Kafka 등 실제 구현체
            ↓
      MySQL / Kafka
```

`domain` 계층은 Spring, JPA를 비롯한 어떤 프레임워크도 의존하지 않습니다. DB 접근 코드(`infrastructure`)를 인터페이스(포트) 뒤로 감춰, 테스트 시 실제 DB 없이 순수 로직만 검증할 수 있습니다.

## 설계 결정 노트

프로젝트 진행 중 내린 주요 판단과 근거입니다.

**DB 스키마를 도메인별로 분리한 이유**
기존 실무 프로젝트에서 여러 배포 단위(`app/web`, `admin`, `batch`)가 하나의 DB를 공유하는 "분산 모놀리스" 구조로 인해, 한 모듈의 스키마 변경이 다른 모듈에 영향을 주는 문제를 경험했습니다. sallim은 물리 DB는 하나로 유지하되 스키마 단위로 소유권을 분리해 이 문제를 구조적으로 방지했습니다.

**테스트 대역을 DI로 주입하는 이유**
프로덕션 코드에 `if (환경 == 테스트)` 같은 분기로 가짜 데이터를 리턴하는 방식은 그 분기 자체가 운영 배포물에 포함되어, 설정 실수 시 운영 환경에서 가짜 데이터가 노출될 위험이 있습니다. sallim은 Repository를 인터페이스(포트)로 분리해, 운영에서는 JPA 구현체를, 테스트에서는 Mock을 외부에서 조립해 주입하는 방식을 사용합니다. 테스트 전용 코드는 운영 배포물에 포함되지 않습니다.

**청결도 모델을 시간 경과와 완료개수 중 하나가 아닌 통합안으로 정한 이유**
두 방식을 각각 시뮬레이션한 결과, 순수 시간 기반은 체크리스트 UX와 충돌하고(할 일이 밀리지 않았는데도 더러워 보임), 순수 개수 기반은 방치 기간을 구분하지 못하는 문제가 있었습니다.

**React Native를 선택한 이유**
Kotlin 기반 Compose Multiplatform도 검토했으나, 배우자가 iOS 사용자이고 Compose의 iOS 지원이 상대적으로 이른 단계라는 점, 그리고 타깃 포지션이 서버 개발자라 프론트엔드 언어 선택이 면접 평가에 미치는 영향이 적다는 점을 고려해 생태계가 더 성숙한 React Native로 결정했습니다.

## 프로젝트 구조

```
sallim/
├── bootstrap/       # 실행 진입점, 모든 모듈 조립 (@SpringBootApplication)
├── household/        # 가구·가구원·권한 (공유 기반)
├── chore/            # 집안일 — 방/할 일/청결도
│   └── src/main/kotlin/sallim/chore/
│       ├── domain/         # Room, ChoreDefinition, ChoreInstance, RecurrencePolicy 등
│       ├── application/    # 유스케이스 서비스
│       ├── infrastructure/ # JPA 구현체
│       └── api/            # REST 컨트롤러, 스케줄러
├── calendar/         # 캘린더 (예정)
└── ledger/           # 가계부 (예정)
```

## 로컬 실행

```bash
# MySQL, Redis, Kafka 등 인프라 기동 (예정)
docker compose up -d

# 애플리케이션 실행
./gradlew :bootstrap:bootRun

# API 문서 (Swagger UI)
open http://localhost:8080/swagger-ui.html
```

> 통합 테스트는 Testcontainers를 사용하므로 Docker가 실행 중이어야 합니다.
